# W6-06 — Coherence + Craftsmanship Amendment

Date: 2026-09-06

Status: **BINDING AMENDMENT WHEN MERGED — design/specification only; production implementation not authorized**

This amendment changes the W6-06 design method after direct product-owner review of PR #201.

It overrides any conflicting W6-06 requirement that treats selection among three visual themes as the primary design decision.

The product-owner finding is:

> The core frontend problem is not that Zen Canvas has the wrong visual style. The core problem is that its screens do not feel like one product, and the execution quality of small visual/interaction details is too low. Theme variations that preserve the same underlying inconsistencies do not solve the problem.

PR #201 is therefore superseded and intentionally not merged.

## 1. Revised problem statement

W6-06 must solve two coupled problems.

### A. Product coherence

Every major surface must feel generated by the same design grammar:

- same shell hierarchy;
- same page-header anatomy;
- same content-edge and pane rules;
- same control heights and density logic;
- same typography scale;
- same radius hierarchy;
- same border and elevation logic;
- same toolbar/command hierarchy;
- same list/grid row grammar;
- same Inspector/Sheet grammar;
- same selected/focus/hover/disabled states;
- same loading/empty/error/unavailable/recovery language;
- same icon family, size ladder and optical alignment;
- same animation timing and interaction restraint.

A page is not allowed to invent a new visual dialect merely because its workflow is different.

### B. Craftsmanship

The target is not merely "consistent enough". The redesign must define and later permit verification of the small details that create desktop-product quality:

- 1px alignment and separator placement;
- exact control and row heights;
- optical rather than purely mathematical icon centering;
- baseline alignment between icons, labels, shortcuts and values;
- text truncation and line-height behavior;
- predictable internal padding;
- edge insets and scroll-area endings;
- corner-radius transitions between nested surfaces;
- hover/pressed/focus transition quality;
- focus-ring geometry and focus restoration;
- selected state that does not fight keyboard focus;
- disabled states that remain legible;
- loading states that do not cause layout jumps;
- empty/error states that do not look like unrelated marketing cards;
- popover/dialog anchoring, shadow, edge clearance and escape behavior;
- scrollbar and overflow behavior;
- narrow-window compression order;
- Chinese/English text expansion without broken rhythm;
- Light/Dark parity beyond simple color substitution.

## 2. Revised W6-06 process

### Phase A — Cross-surface coherence audit

Before another visual prototype is treated as a candidate, create a concrete inventory from current production and W6-05 evidence.

Audit at minimum:

- Window/titlebar
- Product sidebar
- App-level page heading
- Workspace command bar
- Local navigation
- Search field
- Buttons / icon buttons
- Segmented/toggle controls
- Inputs / selects / switches
- Toolbar
- Notice / status strip
- State block
- Card / panel / content surface
- List row / grid item
- Table header
- Selection
- Keyboard focus
- Inspector
- Side Sheet
- Dialog
- Popover / menu
- Tooltip
- Toast
- Preview chrome
- Settings row/section
- Empty/loading/error/unavailable/recovery states
- Scrollbars / overflow / separators

For every primitive/surface record:

1. current implementations/variants;
2. places where the same semantic role uses different anatomy or dimensions;
3. page-local one-off styling;
4. conflicts between existing design docs and current production;
5. canonical target anatomy;
6. variants that should remain;
7. variants/patterns that W6-07 should delete or consolidate.

The audit must distinguish architecture differences from accidental presentation differences.

### Phase B — Single Zen UI grammar

Define **one** system before designing whole pages.

The system must freeze:

- spacing scale and allowed composition gaps;
- typography roles and exact line-height/weight rules;
- control-size ladder;
- icon-size ladder and stroke/optical rules;
- radius ladder;
- border/divider ladder;
- elevation/shadow ladder;
- semantic color roles;
- surface hierarchy;
- content-edge/inset rules;
- page-header and section-header anatomy;
- toolbar/command hierarchy;
- list/grid/table grammar;
- Inspector/Sheet/Dialog/Popover grammar;
- state grammar;
- motion grammar;
- responsive collapse order;
- Light/Dark rules;
- Chinese/English rules.

The system must identify the single source of truth that W6-07 should implement or consolidate around. Existing `--zc-*` tokens may be preserved/rationalized, but duplicate semantic implementations must not remain indefinitely.

### Phase C — Representative high-fidelity reconstruction

Only after Phase B is coherent, produce representative target experiences for:

1. Overview
2. File Library
3. Quick Preview
4. Settings

These are **not four independent mockups**. They must visibly prove that one system can express four different workflows.

Review should explicitly ask:

- do page edges line up across screens?
- do titles, toolbars and body starts share the same rhythm?
- do buttons/fields feel identical when they have the same semantic role?
- do secondary/advanced controls recede consistently?
- do empty/error/degraded states share one grammar?
- does Preview feel like part of Zen Canvas rather than a separate application?
- does Settings feel like the same product rather than a generic admin panel?

### Phase D — Craftsmanship acceptance

No representative target is accepted solely because its broad layout looks correct.

Each target must pass an explicit detail review covering:

- pixel/edge alignment;
- spacing consistency;
- baseline alignment;
- typography hierarchy;
- icon sizing/centering;
- control sizing;
- border/radius consistency;
- surface/elevation consistency;
- hover/pressed/selected/focus/disabled states;
- loading/empty/error/unavailable states;
- scroll/overflow behavior;
- narrow-window behavior;
- Light/Dark parity;
- Chinese/English fit;
- keyboard/focus behavior at specification level.

Any visible one-off pattern must be justified or removed.

## 3. Theme exploration policy

Multiple aesthetic themes are now **optional**, not a required acceptance gate.

If alternatives are explored, they may vary brand expression only after the same structural UI grammar and craftsmanship standard are fixed.

Do not present three palettes with nearly identical underlying component quality and call that product exploration.

The selection question is no longer:

> Which skin looks best?

It is:

> Does every surface now feel like the same meticulously designed Zen Canvas product?

## 4. Required new W6-06 outputs

The following replace the previous mandatory "three comparable visual directions + selected direction" requirement:

1. W6-05 evidence synthesis / design brief.
2. **Cross-surface coherence audit and inconsistency matrix.**
3. **Canonical component/surface anatomy specification.**
4. **Zen token/metric system** with exact dimensions/roles, not just a palette.
5. Shared shell/navigation specification.
6. Cross-product state grammar.
7. **Craftsmanship/detail acceptance checklist.**
8. One coherent high-fidelity Overview target.
9. One coherent high-fidelity File Library target.
10. One coherent high-fidelity Quick Preview target.
11. One coherent high-fidelity Settings target.
12. Wide/medium/narrow rules.
13. Chinese/English and Light/Dark guidance.
14. Accessibility/focus/keyboard design guidance without certification claims.
15. W6-07 implementation/consolidation handoff.
16. W6-08 Preview handoff.
17. Final decision: `W6-06 COMPLETE — PROCEED TO W6-07 RECONSTRUCTION`, or documented blocker.

## 5. Canonical-authority expectation for W6-07

W6-06 must identify visual duplication debt before W6-07 starts.

Current repository evidence already shows presentation authority spread across locations including:

- `src/styles/tokens.css`;
- `src/styles.css`;
- `src/utils/tw.ts`;
- `src/components/ui/*`;
- `src/views/shared/ui.ts`;
- feature-local Tailwind/class compositions.

W6-06 does not modify those production files, but its handoff must state what becomes canonical and which duplicate/legacy patterns should be retired.

A semantic role such as a selected chrome toggle, panel, row, toolbar or page header must not continue to have several visually incompatible implementations after W6-07.

## 6. Design-quality bar

W6-06 is not complete when a reviewer merely says "the colors are nicer" or "the new layout is cleaner".

It is complete only when a reviewer can move among Overview, File Library, Quick Preview and Settings and reasonably conclude:

> These are clearly different jobs, but every measurement, interaction state and visual decision feels like it came from one product team and one design system.

The expected quality is deliberate desktop software craftsmanship, not a themed collection of web components.

## 7. Boundaries unchanged

This amendment does not authorize:

- production `src/` or `src-tauri/` edits;
- broad Tailwind/React/Tauri reconstruction during W6-06;
- backend/schema/authority changes;
- a second Preview architecture;
- weakened safety or AI boundaries;
- W6-07 activation;
- release/tag/version/publication work.

Native whole-product regression remains a stage-level gate owned by W6-09.
